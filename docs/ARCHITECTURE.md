# Architecture

Arliz is the content repository for one continuous book published as three volumes. It owns editorial structure, chapter sources, volume metadata, bibliography, figures, and the final PDFs. It should not own a second implementation of the shared publishing toolchain.

## Ownership boundaries

| Component | Responsibility |
|---|---|
| Arliz source tree | Chapters, front/back matter, volume configuration, book-specific template and editorial rules |
| [Papyrxis Workspace](https://github.com/papyrxis/workspace) submodule | Shared LaTeX components, generated preset, common Python publishing utilities and shared document scaffolding |
| Makefile and scripts/volumes | Thin project-specific orchestration: generate each configured volume and invoke LaTeX |
| [Pipeline](https://github.com/m-mdy-m/pipeline) | Provider-neutral CI stages and the reusable LaTeX toolchain preset |
| [gix](https://github.com/m-mdy-m/gix) | Branch flow and semantic-version operations |
| [psx](https://github.com/m-mdy-m/psx) | Repository structure and quality policy |

## Build flow

`make build` is the single entry point used locally and by CI:

1. Remove stale PDFs and generated volume entry points.
2. Initialize the Workspace submodule and regenerate `.pxis/preset.tex`.
3. Read each `configs/volumes/*.conf` file.
4. Generate a standalone root-level `.tex` entry from `main.tex`.
5. Compile it with `latexmk` and Biber where requested.
6. Copy each completed PDF to `build/` and verify all configured volumes.

The volume-specific scripts remain because the three-volume structure is a property of Arliz, not a generic responsibility of Workspace. Shared LaTeX components and generic publishing operations belong in Workspace.

## Generated files

- `.pxis/` is regenerated by `make sync`; do not edit it directly.
- Root-level `*_ARLIZ_*_Volume_*.tex` files are generated build inputs; edit the source files under `volumes/`, `frontmatter/`, and `backmatter/`.
- `build/` contains generated PDFs and LaTeX intermediates.

## CI and releases

The reusable `.github/workflows/build.yml` workflow runs the Pipeline LaTeX preset for quality, build, unit tests, and PDF verification. The CI workflow calls it for pull requests. The rolling pre-release and versioned release workflows call the same build workflow, so release artifacts cannot use a different build path.

A push to `main` publishes or replaces `latest-pre-release`. A version tag publishes a versioned GitHub Release. Release assets are staged with deterministic collision-resistant names.

The repository uses the main/develop flow configured in `.gix/config`. Pull requests for ongoing work target `develop`; reviewed integration into `main` updates the rolling pre-release.
