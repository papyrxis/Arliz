# Architecture

Arliz is the content repository for one continuous book published as three independently buildable volumes. It owns editorial structure, chapter sources, volume metadata, bibliography, figures, and project-specific LaTeX presentation. It does not implement a second publishing engine.

## Ownership boundaries

| Component | Responsibility |
|---|---|
| Arliz source tree | Chapters, front/back matter, volume configuration, book-specific template and editorial rules |
| workspace.yml | Schema-v2 collection: the three volume documents and their editions |
| Papyrxis Workspace v0.5.1 | Shared Python build engine, safe build planning, isolated outputs, manifest, PDF verification, and reusable LaTeX resources |
| .pxis/ and configs/ | Project-owned preset snapshot and Arliz-specific LaTeX overrides |
| scripts/volumes/ | Thin Arliz adapters: validate volume inputs, generate the TeX entry point, and delegate compilation to px |
| Pipeline | Shared CI stages and the reusable LaTeX toolchain preset |
| gix / psx | Git flow and semantic versioning / repository quality policy |

Workspace is installed from the immutable v0.5.1 wheel pinned in .ci/locks/python-requirements.lock. Consumer checkouts do not need a Workspace repository clone or Git submodule.

## Build flow

make build is the single entry point used locally and by CI:

1. Clean previous Workspace outputs and temporary generated entry points.
2. Generate one TeX entry point for each configured volume under .generated/<volume>/.
3. Invoke the Workspace schema-v2 collection builder for all three documents.
4. Let Workspace compile each edition into an isolated output directory and write build/manifest.json.
5. Verify the manifest, its PDF hashes, and Arliz's expected volume-to-output mapping.

The generated entry points use the repository root as their working directory. Existing relative input, figure, bibliography, and front-matter paths therefore retain their current meaning. Editorial sources are not relocated.

## Generated and maintained files

- .generated/ contains temporary TeX entry points; do not edit or commit them.
- build/ contains Workspace outputs, intermediates, and manifest.json.
- .pxis/ is a committed project-level preset snapshot. It is refreshed deliberately from the pinned Workspace shared components, with files in configs/ taking precedence. It is not regenerated by a submodule command during every build.
- Source content stays under volumes/, frontmatter/, and backmatter/.

## CI and releases

The reusable .github/workflows/build.yml workflow installs the pinned package, runs the Pipeline LaTeX preset for quality/build/tests, and uploads all three nested PDF outputs. The pull-request CI workflow, rolling pre-release, and versioned release workflow share that same build path. Release asset staging recursively collects PDFs from the Workspace output tree and keeps deterministic collision-resistant names.

The repository uses the main/develop flow configured in .gix/config. Pull requests for ongoing work target develop; reviewed integration into main updates the rolling pre-release.
