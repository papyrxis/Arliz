# Contributing to Arliz

Thank you for your interest in contributing to **Arliz** — an open-source LaTeX book exploring Arrays, Reasoning, Logic, Identity, and Zero, organized as three independently-buildable volumes. Corrections, new examples, diagrams, whole chapters, and build-tooling improvements are all welcome.

> **Maintainer contact:** bitsgenix@gmail.com

---

## 1. Before You Start

1. **Clone the repository, including submodules.**

   ```bash
   git clone --recurse-submodules https://github.com/papyrxis/Arliz.git
   cd Arliz
   ```

   If you already cloned without `--recurse-submodules`:

   ```bash
   git submodule update --init --recursive
   ```

2. **Install a LaTeX distribution.** Any full TeX Live install (or equivalent) works. The build uses `pdflatex`, `latexmk`, and `biber`, all of which must be on `PATH`.

3. **Install `bash` and `make`.** The build scripts use bash-specific syntax; `make` is optional but wraps everything in short target names.

4. **Be comfortable with basic Git/GitHub.** Fork the repository, then branch from `main` for any change (for example `feature/vol1-ch3-floating-point`, `fix/vol1-broken-xref`).

---

## 2. Repository Layout

A quick map — see [`docs/ARCHITECTURE.md`](./ARCHITECTURE.md) for the full explanation of how it fits together.

| Path | What lives there |
|---|---|
| `main.tex` | Shared template for all volumes. Never compiled directly. |
| `configs/volumes/volN.conf` | Per-volume metadata, chapter list, back matter list. |
| `volumes/volN/chapterNN/` | Chapter content for volume `N`. |
| `volumes/volN/volN.tex` | The volume's chapter index — `\input{}` entries in reading order. |
| `frontmatter/`, `backmatter/` | Shared and per-volume front/back matter. |
| `references/arliz.bib` | Bibliography, cited with `\autocite{key}`. |
| `covers/`, `images/` | Cover art and in-text images. |
| `configs/*.tex` | Local overrides for a small set of preset components (see §6). |
| `.pxis/` | **Auto-generated.** Regenerated by `make sync` from `workspace.yml`. Never edit by hand. |
| `scripts/volumes/` | `generate.sh`, `build.sh`, `clean.sh` — the actual build logic. |
| `build/` | Build output. Gitignored — never commit anything here. |
| `docs/` | This guide, plus `ARCHITECTURE.md`, `VOLUMES.md`, `WORKFLOWS.md`, `CHANGELOG.md`. |

## 3. Reporting Issues

Open an issue using the template that matches your case:

- **Bug Report** — something doesn't build, a reference is broken, output looks wrong. Include the affected file (e.g. `volumes/vol1/chapter01/chapter01.tex`) and the exact command you ran.
- **Feature Request** — a new chapter, macro, or tooling improvement.
- **Documentation Update** — a correction to `docs/`, the README, or a config file.
- **General Inquiry** — anything else.

Search existing issues first; if you find a match, comment there instead of opening a duplicate.

## 4. Building Locally

```bash
make vol1      # Volume I  — Zero to Bit
make vol2      # Volume II — Silicon Horizon
make vol3      # Volume III — Array Odyssey
make volumes   # all three
```

Each target cleans the previous build for that volume, generates the volume's `.tex` file from `main.tex` + its `.conf`, runs `latexmk` (`pdflatex` + `biber`, multiple passes), and writes the PDF to `build/`.

If you'd rather compile manually (e.g. in TeXstudio), generate the `.tex` file without running `latexmk`:

```bash
make generate-vol1
```

Open the generated file and compile with `pdflatex` + `biber` yourself. **Never edit the generated `.tex` file or `.pxis/preset.tex` directly** — both are build artifacts, overwritten on every build. If you changed `workspace.yml` or anything under `configs/`, run `make sync` to regenerate `.pxis/preset.tex`.

Full command reference and troubleshooting: [`docs/WORKFLOWS.md`](./WORKFLOWS.md).

## 5. Adding or Editing Content

**Decide which volume a topic belongs to** before writing anything — see [`docs/VOLUMES.md`](./VOLUMES.md). As a rule of thumb: encoding and representation → Volume I, hardware and execution → Volume II, arrays themselves (structure, algorithms, applications) → Volume III.

**To add a chapter:**

1. Create the chapter file under `volumes/volN/chapterNN/chapterNN.tex`.
2. Add an `\input{volumes/volN/chapterNN/chapterNN}` line in `volumes/volN/volN.tex`, positioned so its prerequisites are already covered earlier in the file.
3. Run `make volN` and confirm it compiles with no new warnings or undefined references.

You can scaffold step 1 with the chapter generator instead of writing the skeleton by hand:

```bash
make chapter ARGS='-p 1 -c 3 -t "Chapter Title"'
```

(`-p` = volume number, `-c` = chapter number, `-t` = title.)

**Images** go under `images/` (in-text figures) or `covers/` (cover art only) — never inline elsewhere. **Bibliography entries** go in `references/arliz.bib`; cite them with `\autocite{key}`, matching the style already used in Volume I, Chapter 1.

## 6. LaTeX Conventions

- **Encoding and line endings:** UTF-8, Unix (`LF`).
- **Don't add `\usepackage{}` inline in chapter files.** Packages live in the workspace preset. If you genuinely need a new one, edit `workspace.yml` plus the relevant component, then run `make sync`. Only these files under `configs/` are meant for direct local overrides: `code.tex`, `colors.tex`, `fonts.tex`, `env.tex`, `graphics.tex`, `bibliography.tex`, `boxes.tex`.
- **Use the existing custom environments** rather than ad hoc formatting:
  - Narrative framing: `chapterintro`, `sectionintro`, `subsectionintro`, `historical`
  - Theorem-like blocks: `definition`, `theorem`, `example`, `implementation`
  - Callouts: `notebox`, `tipbox`, `warningbox`, `examplebox`, `definitionbox`
- **Use the existing macros** for recurring notation rather than retyping it: `\bigO`, `\Naturals`, `\Integers`, `\Reals`, `\Prob`, `\Expect`, and so on (see `.pxis/components/commands/base.tex`). Use `\term{}` for a term's first occurrence and `\keyword{}` for emphasis.
- **Label everything you might reference.** Add `\label{}` immediately after section headings (e.g. `\label{sec:floating-point}`), and use `\ref{}` rather than a hardcoded number or chapter name.
- **Don't commit build artifacts.** Everything `.gitignore` already excludes (`*.aux`, `*.log`, `*.toc`, generated volume `.tex` files, `build/`, etc.) should stay out of your diff.

## 7. Pull Request Process

1. Branch from `main`, push your branch, open a PR against `main`.
2. Fill out the PR template completely — it checks that the affected volume(s) still build with `make volN`, that new images and macros went in the right place, and that no build artifacts are included.
3. Keep commits focused: one logical change per commit (see commit format below).
4. A maintainer typically reviews within a few business days. Larger content PRs may take longer.

---

## 8. Commit Message Guidelines

Arliz uses semantic commit messages:

```
<type>(<scope>): <short summary>

<body, optional but encouraged>

<footer, e.g. "Closes #52">
```

**Types:** `feat`, `fix`, `docs`, `chore`, `style`, `refactor`, `test`.

```
feat(vol1-ch3): add worked example for IEEE-754 rounding

Added a step-by-step rounding example to chapter01/floating-point
section, using the existing `example` environment.

Closes #61
```

## 9. Editorial Guidelines

- **Terminology:** the project is organized into **volumes**, not "parts" — that naming was retired during the restructure, so avoid reviving it in new content.
- **Tone:** direct, technically precise prose. Avoid first-person unless a passage is explicitly a personal note (the volume "About This Volume" sections are the one place that's appropriate).
- **Spelling:** American English (organization, behavior, color).
- **Define terms on first use**, wrapped in `\term{}`.
- **Cross-reference, don't hardcode:** `\ref{sec:...}`, never "see page 42."
- **Sourcing:** factual or historical claims tied to a specific source should carry `\autocite{key}` against an entry in `references/arliz.bib`. Distinguish established fact from interpretation, especially for historical material.
